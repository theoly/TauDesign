## 2. 不附图是否丢上下文

**现在会丢失部分上下文，不会必然丢失所有上下文。** 用户原提示、明确引用页面、当前项目规则/主题仍可能被加载；原图细节、上一份功能规划和未重传的文字附件则不能保证保留。仅凭“如附件图片样式”不足以重新获得字段、排版与文案。

目标改为三种清楚区分的操作：

1. **继续生成（复用图片解析与规划）**：默认恢复方式；不重复发送已经成功解析的图片，保留来源与授权。
2. **重新解析参考图**：图片解析失败、图片或裁剪变化、用户明确要求重新观察时使用。
3. **忽略图片，按文字重新设计**：明确放弃图像约束的新任务；无有效解析时提示哪些内容无法保留。不是无损重试。

旧消息若只有含图规划、没有独立的图像证据快照，不能声称完整保留视觉细节。可验证其来源后保留其中已整理的信息作为历史证据；必要时解析原图一次。原图丢失则说明缺口，允许用户明确选择文字降级。

## 3. 推荐目标流程：一次提交，分阶段执行

```text
用户需求 + 当前页/选中元素 + 项目规则 + 文档 + 图片文件
  → 输入冻结与预检
  → 图片证据提取（有有效缓存则跳过）
  → 功能/信息/交互规划（有有效规划则跳过）
  → 选择复制局部修改 / 主体写入 / 最多3区域补丁
  → 代码生成（使用代码档位，按能力控制思考）
  → 完整性、授权、媒体、Token与实际渲染校验
  → 必要时一次受控恢复并重验
  → 候选对比与采纳，或返回明确阻断
```

“一次正常调用成功”的目标应定义为**用户提交一次即可完成，不需要反复手动重试**，不能承诺只有一次 HTTP 请求或任何模型100%成功。图片解析、规划、代码生成通常需要2–3次模型请求；缓存命中或已确认的局部修改可更少。不能为了减少请求合并所有阶段，重新放大同一失败风险。

### 3.1 统一输入合同与恢复身份

建立版本化 `TaskInputSnapshot`/`RetryContext`，复用现有 TaskContract、Journal、资源和恢复服务，不新建第二套权威存储。包含：

- 工程身份、原需求及显示文本、明确目标/元素、原页和CSS/L4基线指纹；
- 原始动作、只读风格参考、用户已确认范围、保护节点；
- 文字附件的路径、内容指纹与独立文件引用；
- 设备、导航策略、主题/设计库、项目知识和决定的版本；
- 图片资产引用、实际传输版本/裁剪身份、图像证据、规划及生成方式；
- 各阶段 Provider/model、有效能力配置与参数策略、预算和父子尝试关系。

重试读取该合同，不能重新依赖当前选中画框或从聊天字符串推断落点。工程/目标/规则等已变更时显示差异并重新验证；不把旧快照静默覆盖当前页面。保留原尝试及费用，禁止把历史记录重新解释成新执行授权。

### 3.2 图片单独处理，但属于同一任务

增加 `ReferenceEvidence`：图片/裁剪/解析版本指纹、可辨识文字和字段、分组顺序、组件与状态、布局关系、视觉约束、区域坐标、可读性限制和不确定项，以及实际解析模型来源。

- 使用现有 Vision 档位与专用图片字段；图片二进制不进入文本 Prompt、HTML、CSS或会话 JSON。仍走 Rust/Vite 代理。
- 图片独立落盘，代码模型只接收有关的结构化证据、规划及素材外链。参考截图不会自动作为页面插图使用。
- 缓存以实际图片字节、裁剪/变换、解析合同及模型配置版本等绑定；相同图可复用视觉观察，本轮相关证据选择仍按当前要求计算。内容变化即失效。
- 长图不能简单压到所有文字不可读。按目标裁剪、受控多片观察并保留坐标关系；片数和预算必须预先有界。字段辨识不了就标注不确定，不能编造。
- 图片只是参考资料；不执行图片内指令，不从截图推断真实权限、价格或后端行为。
- 不做单独用户聊天、不额外默认上传公共图床、不在规划与代码阶段反复附同一张图片。
- 精确复刻/复杂视觉细节不能承诺仅靠摘要无损。该模式保留可用的视觉生成/核对步骤，并明确其能力与成本；普通表单修改默认采用证据→代码分离。

### 3.3 统一阶段模型和参数策略

按 `视觉观察 / 功能规划 / 代码生成 / 校验修复` 决定角色及参数；图片存在不再自动把整个任务都切给 Vision。

- 默认机器产物阶段采用可控的低思考/非思考策略，普通问答仍保留其独立配置。
- 将 `thinking`、`enable_thinking`、Schema格式、输出上限等能力集中到端点+模型绑定的能力档案；已验证的适配器只发送其支持字段。未知兼容端点不因为模型名或 ID 含 custom 就乱发厂商参数。
- 当前名称推断出来的容量仅为估计，不能当实测能力。优先显式配置或已验证元数据；端点/模型变化使原配置失效。
- 如果端点只支持思考，预留正文空间、缩小代码目标，或提示选择已配置的合适代码模型；不能承诺关闭无效参数能解决所有端点。
- 保留规划的原模型来源。允许规划交给另一代码模型执行时，新增明确的阶段来源/派生合同并重验；不改写原规划凭证来骗过现有绑定校验。

### 3.4 功能规划与局部修改

本例已有页面且用户指定新增表单并保留在当前页：先获得图片中的字段/分组证据，再规划新增控件与静态交互，复制原页，仅修改合适的表单区域；不默认整页重写或跳到其他页。

- 已有匹配的有效规划时不重复规划；旧规划不匹配时说明原因。
- 可按一次提交完成必要的内部规划，但不为用户已明确指定的改法再次列选择清单。
- 只有“优化一下”等宽泛意图才先分析、展示选项并等待选择。
- 所有 patch 经 DOM/稳定 nid 和授权范围校验；布局需要父容器时只能在原授权可支持的范围内扩展，不能以自动修复扩大页面修改范围。

### 3.5 代码规模与预算

沿用现有四种写入模式，不再开发一套竞争的分区协议：普通主体一次写、4–6主要区块先规划再一次写、7+或超过45KiB或实际容量放不下时最多3区域 patch、派生副本仅改 mutableRegions。

- 所有入口，包括普通重试、无图恢复、结构化修改、整页重设计，必须保留原生成选项和合同。
- 在请求前核对实际生效输出上限；代码填写16384但被能力档案压为8192时，界面与预算必须显示有效值。
- 本轮总预算统一覆盖图片解析、规划、生成、续写和自动修复；动态分配并预留未执行步骤最低额度，额度不够在发送前解释，不能中途擅自扩容。
- 精简重复注入：公共规则一次、原页基线一次、针对性资料和证据一次；完整必需原文、授权和保护条件不能被静默裁掉。
- 聊天历史仅作辅助，对重复错误压缩为诊断摘要，保持原消息可查，不能让失败日志占据主要模型上下文。

### 3.6 按原因恢复，禁止相同请求循环

| 故障 | 处理 |
| --- | --- |
| `length`，正文0，只有推理 | 标记“思考耗尽/未取得代码”，不能续写；在有效能力允许、父预算足够时，最多一次改变产物策略的恢复，优先关闭可控思考或缩小局部目标。参数不支持时给出明确选择，不能原样无限重试 |
| 已有未闭合HTML，`length` | 保留已验证前缀并受限续写；验证消息、模型、来源及前缀；不能把纯推理当作前缀 |
| 图片解析失败 | 仅重试解析阶段；没有解析证据不能声称“复用图片信息” |
| JSON格式或Schema错误 | 保留输入及第一份错误证据，限一次格式修复；不得删功能或清空真实关键问题绕过校验 |
| 网络中断/无活动超时 | 区分连接、首事件、正文、已结束状态；按阶段和预算处理。POST可能已计费，记录重发风险及实际发送次数；不假设可断点恢复 |
| 鉴权、余额、限流、无效参数 | 分别提示；遵守 Retry-After 和取消信号；不把它们混作图片错误或无条件扩大超时 |
| 页面通过生成但布局/质量失败 | 用一次有范围的修复再验；仍失败停在候选外，原页不动 |

自动恢复上限应由单一恢复控制器管理，覆盖内部Schema纠正/续写/外层修复，分别记账且受父额度限制；不能每层各算一次形成重试放大。

超时配置统一区分连接/无活动/整任务，并由实际传输层落实；收到推理事件表示仍有活动，但不代表取得代码或已成功。输出耗尽不能靠延长超时解决。

## 6. 必须通过的验收

1. 回放“规划成功→代码纯推理→length→用户恢复”：不重复无效请求、不误报断网、有据可查，原页不变；可恢复分支最终取得完整候选，不能把失败包装成成功。
2. 实际经过请求编码器校验支持/不支持/未知端点的请求字段；不使用直接Mock HTML返回替代该证据。
3. 有有效图片解析时，恢复请求没有图片字段、没有base64文本，但保留图片字段/分组/必须文案及来源；没有有效证据时明确降级，不伪称保留。
4. 文字附件、只读风格参考、writeStrategy、wholePageRedesign、元素范围、已确认修改项在所有重试分支保持一致；请求或基线变化正确失效。
5. 截图对应表单使用原页副本和已授权区域，新增字段、当前页展示、操作文案及布局完整；不改无关业务，不生成可执行后端。
6. 请求耗尽、上下文不足、坏图、缺失文件、不支持Vision、Schema失败、未知finish reason、断流、取消、重复点击与迟到回调均有明确终态。
7. 每次解析/规划/生成/纠错的真实发送次数、用量、有效cap可核对；内部与外层恢复不会超出父预算。
8. 工程、会话、草稿中的媒体为独立文件引用；图片专用字段允许编码，HTML/PNG导出仅临时副本可内联；资源丢失不可静默生成假图。
9. 候选校验及三种采纳操作、Undo/Redo、保存重开不退化；导入页既有CSS/Token/导航规则保持。
10. `pnpm test` → `pnpm run type-check` → `pnpm build` 全通过并归档；Chromium/WebKit覆盖移动与PC，computer use验证真实错误卡片与恢复操作。真实Provider用合成资料验证，模型拒绝/限流/容量不足如实记为失败，不能选择性删记录。

## 7. 提请确认的决策

建议确认：**默认采用图片先独立解析、证据/规划可复用、代码模型只负责生成；完整保留重试输入，按真实故障分类恢复。** 对精确复刻保留必要的视觉核对路径。以“一次用户提交完成”为目标，不保证单次HTTP或所有Provider必然成功；不得自动放宽预算、授权范围或质量门禁。

用户已确认原方案实施，并随后确认本节图片压缩/哈希/独立视觉解析补充设计。下文“当前代码实况”仅指 2026-11-11 补充方案编写时。

### 8.1 当前代码实况

- 上传/粘贴在 `ChatDrawer.tsx` 使用 `FileReader.readAsDataURL`，未发现统一的发送前压缩、尺寸缩放或自适应切片。
- `referenceCrop.ts` 支持按用户选区裁剪，以PNG重编码；裁剪不是有损压缩，也不保证文件更小。
- `screenCapture.ts` 的页面截图使用JPEG quality=0.88，属于画布截图来源，不能据此宣称所有用户附件已压缩。
- `AttachmentStore.save` 使用图片二进制MD5，保存到 `assets/images/{md5}.{ext}` 并复用已有文件；当前任务图片指纹还使用8位内容指纹，两者不能替代新的强内容校验。
- 当前规划和生成可能多次携带实际图片；尚未落实“只解析一次，后续只传证据”的默认链路。

### 8.2 原图与发送副本分离

```text
原图字节 → 类型/解码/像素上限校验 → 按内容哈希独立落盘（不覆盖）
        → 根据目标选择裁剪、缩放、重编码/切片 → 发送副本独立落盘
        → Vision专用图片字段 → 结构化图像证据及解析回执
        → 功能规划 / 代码生成 / 普通重试：只传有关证据与素材链接
```

- 新增资源使用SHA-256命名/身份；旧MD5路径兼容读取，不批量重命名历史文件。显式记录hash算法；原图与派生图各自按实际字节计算哈希。
- manifest记录来源hash、发送hash、尺寸、格式、字节数、裁剪坐标与变换版本；同一原图不同选区/压缩版本不能混用缓存。
- 原图独立保留供用户查看和必要复核；缩略图只用于界面，不能无条件代替模型输入。
- 可在本机生成发送副本并移除不需要的元数据；按实际字节复用已有文件，写入后验证一致性，不能仅凭同名文件存在就信任其内容。
- base64仅是部分Provider专用图片字段的传输编码，目录仍存二进制；本地路径不会成为云模型可访问URL。无需公共图床或额外上传服务。

### 8.3 自适应压缩，不牺牲字段可读性

- 区分截图/表单/线稿与照片。小图和文字截图优先保留无损PNG；照片可选兼容JPEG。透明度、旋转方向、动画首帧等必须显式处理和记录，不无声丢失信息。
- 分开控制文件字节数、解码像素数、长宽边界与Provider视觉成本；压缩字节不等于减少视觉Token。限制解码资源，避免超大图片导致内存耗尽。
- 文字截图优先裁掉无关区域，而不是整图大幅缩小；长图采用有界的“总览+局部片段”，保留坐标与必要重叠并去重。Provider支持多图时可在一次视觉请求中传多个专用图片part；否则串行受父预算限制。初始最多3个细节片段，无法覆盖时提示选择区域，不静默漏掉其余部分。
- 缩放/重编码仅在超出适用限制或确有收益时执行；结果比原图更大则保留较小且清晰的版本。具体阈值按Provider能力与回归样本确定，不以统一JPEG质量值宣称可读性合格。
- 展示实际发送范围和“已优化尺寸/按区域解析”，允许查看原图和发送副本。辨认不清时停止编造字段，展示不确定项；必要时只重新解析相关区域。

### 8.4 解析证据必须可用、可追溯

- 图像证据不是一段自由摘要。分离“可观察事实”“模型推断”“不确定项”，保留原文、字段顺序、必填/状态标识、区域布局、组件和视觉约束，禁止摘要丢失关键标签。
- 通用视觉观察缓存按图像/变换/解析协议/模型能力版本绑定；本轮任务的相关性选择与功能规划再绑定需求/授权/项目规则。这样改用户提示不必重新识别同一张图，也不把旧任务推断当通用图像事实。
- 证据做Schema、长度、来源、媒体编码、坐标及重复信息检查；不可读状态不是“无内容”。限制每阶段字符/输出额度但不静默截断必需原文。
- 界面可查看“从图片识别的信息”及不确定项。用户更正保留为用户来源的覆盖层，原始视觉结果不被篡改；编辑后更新规划/生成身份。
- 结果缓存与生成产物分离。普通重试复用成功阶段；图片或相关证据变化时，仅使受影响的下游步骤失效。

### 8.5 进一步优化及优先级

本轮必做：原图/派生图分离、哈希校验、独立Vision解析与缓存、完整任务恢复、阶段参数统一、父预算与错误分类、必需信息覆盖验证，以及原页局部修改。

可在上述稳定后评估，不作为修复前提：本地OCR辅助提取文字、跨任务缓存配额/LRU回收、复杂复刻的二次视觉差异检查。OCR不取代视觉布局理解，不能添加一个外部OCR服务而不说明新的数据去向；缓存清理必须保留任务仍引用的资源。

精确复刻、模糊小字、图像占比高等情况仍可能需要读取原图或补充局部视觉核对。“后续不重复传图”是普通流程默认，不是禁止必要且有记录的视觉复核；不能声称结构化摘要等价于原图全部信息。
